需要建模的七个维度

先明确关系，再讨论配置页面与存储
01 / TRUST

平台隔离与接入信任

接入应用、签发方、受众及模型/域白名单。平台隔离域由可信配置确定，业务租户属性另行映射。

02 / SUBJECT

主体与代理调用

平台管理员、业务用户和服务主体分别建模；实际调用者 actor 与被代表主体 subject 都进入审计。

03 / IDENTITY MODEL

属性与实体关系

配置用户、角色、组、组织和自定义实体的键与关系路径。身份目录可以独立于业务资源库。

04 / RESOURCE

资源与产品操作

库表列、数据集、Wiki、模型配置与历史分别表达操作授权。管理、使用、编辑和发布互不隐含。

05 / DATA POLICY

行列与字段用途

投影、过滤、关联/分组/计算、脱敏和限额。行规则将实际资源字段绑定到类型化主体属性。

06 / EXECUTION SCOPE

执行范围上限

客户端、Agent、数据集、会话和任务共同收窄已有数据权限；数据集成员配置本身不能授予查询权。

07 / CHANGE & DELIVERY

发布、撤权与敏感交付

草稿与发布版分离，记录策略完整版本、身份模型版本与外部身份新鲜度。执行、模型输入、结果消费和历史回放分别复验；外部撤权需明确检测窗口。

建议依次讨论的四个决策

当前建议，不代表已冻结
A

权限域怎样组织？

建议同一身份模型可复用多个域，一个域可以包含多个资源数据源；首批一次执行明确一个域，域间合并另行设计。

B

多角色权限怎样叠加？

先保留最严合并；单独决定是否引入显式拒绝，以及是否需要区分角色授予和强制约束两层。

C

外部撤权怎样及时生效？

建议严格模式缓冲敏感输出后复验；实时 SSE 需要通知或轮询，并明确最大检测窗口与解析失败行为。

D

首批支持哪些关系？

建议先支持直接外键、单关联表路径和类型化属性；组织递归、复杂多跳与自定义表达式按能力合同扩展。
