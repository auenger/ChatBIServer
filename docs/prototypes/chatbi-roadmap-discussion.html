开始讨论 6 项决策

建议主线：版本收口 → 权限合同 → 受控查询闭环 → 全入口执法 → 只读业务试点 → 按需扩展写回与管理。

事实、建议与讨论倾向分别标注。此页不执行授权、不修改项目计划；正式规划需要我们讨论后另行确认。

为什么调整推进顺序

最初按数据库能力依赖排期。现在对话、Wiki 和数据集已提前交付，应根据实际能力重排交付顺序，保留完整数据库能力的长期目标。

原始路线

P1 连接器→P2 查询与权限→P3 增删改→P4 对象与账号→P5 Wiki / Agent→P6 更多数据库

原规划的统一 Java 领域入口、默认拒绝、显式上下文、Agent 权限收窄和高危操作专用通道继续有效。

当前应优先解决

不同业务用户能否通过可信接入，获得正确的行列、知识和结果范围；撤权后能否停止后续交付。

已有能力足够验证产品价值，权限是从单管理员演示转向业务试点的主要缺口。

将 P5 拆开推进

只读 Agent 的 Run 状态、预算、取消和耗时治理提前到产品试点阶段。

写操作提案、审批与执行继续依赖 P3/P4；更多方言按首批业务系统需求推进。

怎么判断这一阶段真的完成

验收围绕业务请求贯穿身份、查询、知识与交付。配置保存成功、前端隐藏字段或响应改成 ENFORCED，都不能单独代表通过。

首版查询范围应保守到什么程度？

先把单表行列权限测透。无行规则的可解析 JOIN 可按合同支持；涉及行规则的 JOIN、CTE 和子查询，只开放已验证的形态，无法可靠解析或执法的请求拒绝。四方言分别记录 SUPPORTED / PARTIAL / UNSUPPORTED。

严格缓冲是否意味着界面完全没有进度？

可以提供不含敏感资源或结果的阶段状态。敏感正文缓冲后复验再发；进入模型前已做治理与复验，但已发送给模型的数据无法追回。若开放敏感实时流，必须另行定义最大撤权检测窗口、失效方式与失败关闭行为。

哪些能力可以与权限实施同时准备？

业务问题集、试点系统调研、配置交互、Run 合同与性能观测可以同时推进。依赖权限的生产接入与敏感交付，必须通过相应门禁后开放。新增独立业务入口要同步纳入权限覆盖。
