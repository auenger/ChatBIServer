# P2 通用权限模型复核：面向外部业务服务

> 2026-10-13，依据用户补充的核心场景：连接的数据库主要支撑其他业务服务，需要通用身份映射与数据授权。本文是复核与设计建议，未实现、未冻结新合同。
> 修正此前“本地用户管理优先、外部主体只预留”的推进方向。既有 P2 修订的 SQL/Wiki/历史执法要求保留；身份、权限域、存储及首批次须按本文继续细化后落码。已验收的 Docker 包及其文档快照不改写。

## 2. 目标与对象划分

目标：同一套权限内核能够接 CRM、ERP、内部管理系统和服务账号。接入新系统主要增加信任配置、身份映射和策略；不修改核心授权代码，不改变其业务库表结构。

| 对象 | 定位与边界 |
| --- | --- |
| ControlIdentity | MEPER 控制台管理员身份；本地密码只是认证方式之一；不能与业务库角色自动互认 |
| TrustedClient / Issuer | 哪个应用可调用、哪些签发方可信、允许使用哪些身份模型/权限域、调用能力上限；支持多配置，不能仅一组全局服务密钥 |
| SubjectRef | 业务主体稳定标识：受控平台隔离域 + 身份来源/issuer + 外部 sub；业务域内映射再限定 accessModelId；不使用裸用户名作全局唯一键 |
| AccessModel | 可发布、可测试的身份与关系映射；目录源可与业务数据源不同，可复用于多个授权域 |
| EntityDefinition | 可配置实体类型、物理表/键、有效状态与属性映射；USER/ROLE/GROUP/ORG_UNIT 为预设，允许受支持的自定义类型 |
| RelationshipDefinition | 实体之间的直接外键或关联表路径，显式字段、基数与可选深度上限；不靠表名猜关系 |
| ResolvedSubject | 解析后的业务实体键、类型化属性、关系集合、来源版本与有效期；没有强制 passwordHash |
| PermissionDomain | 授权配置与适用边界，关联身份模型、资源范围和可访问客户端；具体定义与旧“一域一数据源”结构的迁移须细化 |
| ResourceRef | 数据源、catalog/schema、表/字段及 Wiki/数据集等受控对象；资源与身份目录解耦，一个主体可授权多个数据源 |
| Policy / Binding | 策略规则与主体选择器绑定；选择器支持具体主体、映射角色/组、受控关系或类型化属性条件 |
| ExecutionScope | 客户端、Agent、数据集、会话/任务的执行上限；不授予主体原本没有的数据权 |

平台隔离域和业务库中的“租户实体”分别建模。外部 tenantId 不能直接选择控制库隔离域；业务库没有租户字段也可正常授权。不以“销售”“财务”或某张 orders 表定义核心类型，这些只能作为测试夹具。

服务账号可作为独立 SERVICE 主体授权；代表用户调用时同时保留 actor（调用应用/代操作人）和 subject（被代表主体）。不能在服务账号和用户权限之间自动择宽使用，也不能把外部 roles=admin 映射成平台超管。

## 3. 三种身份接入方式

1. **业务库目录映射：首批主路径。** 已验证的外部 sub 映射到指定实体，要求唯一、有效；通过配置关系得到角色、组织等信息。
2. **可信声明属性：契约中纳入。** 属性名、类型、可信来源、允许用途及冲突优先级显式配置。签名有效不等于所有 claims 都可用于授权。
3. **外部目录/权限服务：提供者接口。** 为无用户表或已有统一权限服务的系统预留适配；失败、超时、无映射均拒绝，不默认为超管或全字段。

首批只实现明确支持的关系路径和表达式集合；未支持的复杂关系应在模型发布时拒绝，不能“保存成功但运行时忽略”。外部协议选择及具体提供者实现仍需按实际首批接入系统确定，不宣称一次支持任意 IAM。

## 4. 通用策略表达

策略基于逻辑属性与资源字段绑定，例如：

```text
主体属性：businessUserKey / orgKeys / regionKeys（配置产生，不假定固定字段名）
资源规则：某实际负责人字段 = subject.businessUserKey
          某实际区域字段 IN subject.regionKeys
```

系统 A 可映射 sys_user + sys_user_role，系统 B 可映射 employee + employee_profile，两者复用同一语义模板。资源端字段按各自表配置。身份目录位于第三个数据源也应可用，不要求每个业务库复制用户表。

行规则使用带类型的表达式树及参数绑定；字段标识必须来自发布时校验过的元数据。没有配置行规则时不自动添加 tenant/dept 条件；已经配置但必需属性缺失、类型错误或集合为空时不能省略条件放宽查询。

数据权限至少区分：资源可发现、SELECT 投影、过滤、关联/分组/计算使用、脱敏及限额。具体首版能力沿用 P2 修订的保守范围，不因配置支持新主体类型而放宽 SQL 能力。

**策略组合仍是待细化点。** MEPER 已确认“操作取并、约束取最严”；旧通用设计有“显式拒绝优先”。不能直接混成常见多角色权限并集，也不能在本轮静默改为更宽授权。落码前须明确规则的适用域、是否增加 DENY、角色授权与强制约束如何分层；用真值表覆盖多角色、多域、空集合和冲突。未确认新语义前保留已确认的保守规则，新增合同版本不得复用旧版本含义。

有效数据范围受：调用应用上限、主体策略、Agent/数据集/任务范围、系统操作限制共同收窄；实际数据库凭据也必须能执行，但凭据能读不代表主体获授权。数据集/Wiki 使用授权仍需单独检查。

## 5. 可信执行和外部权限变化

```text
上游完成用户认证
→ MEPER 验证调用应用及身份断言，并检查客户端允许使用的身份模型/权限域
→ 按已发布 AccessModel 解析主体、属性和关系
→ 计算资源/字段/行权限与执行范围
→ 服务端签发 ExecutionContext
→ 统一执行、知识检索、模型输入与结果/历史交付检查
→ 审计 actor、subject、client、映射/策略版本及实际结果
```

会话绑定客户端、身份来源/主体、身份模型、授权域与数据范围；不能凭 sessionId 更换用户。跨数据源身份联结必须显式配置，不能按相同用户名或 email 自动认定同一人。密码和业务账号生命周期继续由原业务系统管理；MEPER 控制台提供目录查询、映射预览和授权配置，不默认写回源用户表。

**外部变化不能只靠本地 tenantEpoch。** 业务库直接撤角色/停用户不会修改 MEPER 控制库 epoch。授权戳须补 accessModelRevision 与外部主体/关系新鲜度证据。提供者有可靠版本时重新比较；无版本时首版在关键工具执行、模型输入/最终结果交付前重新解析并比较规范化身份快照。流式期间如何检测变化必须明示：可选失效通知/轮询且声明最大延迟，或在严格配置中缓冲后复验再交付；不能声称本地 epoch 实现了外部权限瞬时撤回。持续读取需超时和预算，过期快照/检测失败停止交付。

## 6. 身份目录查询的工程边界

policy 仍为纯决策模块，不增加 JDBC 或 domain 反向依赖。身份解析由 domain 编排提供者，数据库读取经连接器接口完成。

目录查询在最终用户策略尚未形成前发生，需显式的内部 IDENTITY_RESOLUTION 用途：仅执行已发布 AccessModel 编译出的白名单读取计划，限定目录源/表/列、绑定参数、行数和超时，并审计。该计划也经过执行层的用途与范围校验，不开放任意 SQL 入口；不通过临时超管或递归调用“先解析同一用户才准读目录”的路径实现。具体 SPI 合同应与元数据接口一并先设计和测试。

## 7. 调整后的推进顺序

1. **通用合同与接入配置**：Client/Issuer、SubjectRef、AccessModel/Entity/Relation、Resource/Policy；先画清信任与数据流，确定首批 SQL/关系/属性子集、合并真值表和外部撤权检测契约。
2. **两种异构目录的纵向样例**：两个本地测试业务服务，各用不同表名/键/角色关系；相同 sub 不串域，映射源与资源源可分离，仅改配置即可运行。
3. **可信 API + 主体解析 + 单表行列执法**：实际签名调用、映射唯一性/有效性、参数化行规则和审计，覆盖跨服务冒用/重放/外部撤角色。
4. **Wiki/数据集/Agent/历史全面接线**：沿用之前适配的全入口门槛；全部通过后再开放普通业务主体。
5. **通用配置页面与发布**：接入应用/信任配置 → 身份模型 → 主体目录 → 授权规则 → 有效权限预检与真实读取。最小本地管理账号页面作为控制面配套。

V9/V10 仍只为候选编号；此前 identity/identity_role 七表草案不足以覆盖通用模型，需要先重审 DDL，不能直接按本地用户版建表再补外部字段。超管 seed、默认拒绝、凭据安全、四方言与 Wiki/历史执法原则继续保留。

验收重点：换业务服务只改配置；不同来源同名用户不串权；用户/组/组织均非必填物理表；可选行字段不被强制假定；新增角色不得悄悄扩大权限；外部失效能在已声明窗口内阻止新交付；身份目录读取不能变成业务查询旁路。
